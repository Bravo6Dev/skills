# Vertical-slice architecture

Build a working project foundation and one small reference use case that proves the flow. The reference pattern is a co-located HTTP slice using FastEndpoints for transport and validation, MediatR for dispatch, ErrorOr for expected failures, EF Core for persistence, and separate Domain, Application, Infrastructure, API, and Tests boundaries. Use the user's chosen stack or existing platform constraints when they differ; retain the architectural responsibilities rather than forcing package names. MediatR is commercially licensed from v13; check the current terms for the version you would install before adding it. FastEndpoints' own command bus or plain handler classes fill the same dispatch role without it, so when the project has not already chosen a dispatcher, state the options and let the user choose.

## Discover and decide

Read the target repository's agent instructions, architecture decisions, solution/project files, deployment environment, database requirements, and test conventions. Determine whether this is a new solution or an architecture setup inside an existing solution. If the solution already has an established architecture and the request is one new use case, do not re-scaffold: use `vertical-slice-feature` when use cases are co-located under feature folders in the API project, use `add-feature` when MediatR handlers live under an Application project and Carter modules expose them, and for any other layout stop and tell the user which pattern you found. Preserve compatible existing structure, SDK pinning, package management, CI, and configuration. Choose the database provider, authentication model, API versioning, localization, and external integrations from actual requirements. The database provider, authentication model, and API versioning scheme are costly to reverse: when the requirements do not settle one of them, ask the user instead of defaulting. For any other choice that has no requirement yet, make a small documented default that can be replaced without changing domain code.

Use [the architecture blueprint](references/blueprint.md) for the project graph, setup flow, reference slice, and acceptance checks. Create only infrastructure that the requested product can use now; mark future extension points in concise documentation instead of building unused systems.

## Deliver a working template

1. Establish the solution, project references, dependency injection composition, configuration and secret boundaries, database context and migrations, and API startup. Keep domain rules independent of web and persistence frameworks; place service contracts and shared workflows in Application; implement persistence and external adapters in Infrastructure.
2. Add a small end-to-end reference operation in `Api/Features/<Area>/<UseCase>/` (or the target's equivalent). Its transport request, endpoint, handler, and any validator/response belong together. Wire dispatch, expected-error mapping, validation, authorization policy, API documentation, and cancellation through the complete route. The reference operation should exercise a real persistence path when persistence is in scope.
3. Set up meaningful unit, integration, and HTTP contract test facilities for the chosen stack. Include a runnable build/test command and a minimal CI gate for the CI provider the repository already uses; when it has none, ask the user which provider to target before adding workflow files. Add an automated dependency test (NetArchTest, ArchUnitNET, or an equivalent reflection test) that fails when Domain or Application references API or Infrastructure, or when a type under the API feature folders uses an Infrastructure type directly. Verify dependency injection resolves the reference handler, the route is reachable, persistence works with the real provider where it matters, and documented responses match runtime behavior.
4. Document the feature folder contract, layer ownership, registration rules, migration command, test commands, and decisions that future feature work must follow. Put this where the repository already keeps architecture decisions; when it has no such place, create `docs/architecture/feature-slices.md` and link it from the repository's agent instructions or README, so `vertical-slice-feature` and later contributors find it. Avoid a large generated manual or redundant sample code.

## Guardrails

- One HTTP use case is one slice. Do not duplicate a separate transport DTO and command solely to cross a layer when the API request can safely serve both roles. "Safely" means every client-bindable property is genuine client input: nothing the server decides (caller identity, tenant, role, owner, computed or audit values) can be supplied through body, query, route, or header, and such values come only from claims or server state. When the binding pipeline cannot guarantee that, use a separate dispatch message built by the endpoint. Keep domain behavior out of endpoints.
- Expected business failures are typed results with stable codes and mapped HTTP responses; unexpected failures use the application's exception path. Client input cannot supply trusted identity or authorization decisions.
- API endpoint/validator discovery, MediatR handler registration, service lifetimes, migrations, and test startup must be proven by execution, not assumed from compilation.
- Database migrations and deployment need a compatibility plan when an existing release may still run. Never apply a generated migration to an uncontrolled database merely to validate the template.
- Security baseline for the template: HTTPS redirection and HSTS outside development; an explicit CORS policy when browsers call the API (no wildcard origin together with credentials); unexpected exceptions return a generic error with no stack trace or internal detail; logs carry no secrets, tokens, or personal data; request body and upload size limits are set; every list endpoint has a maximum page size; rate limiting covers anonymous and authentication endpoints; a command a client may retry is idempotent or takes an idempotency key. Report an item that does not apply as **not applicable** with the reason rather than omitting it.
- This skill creates the architecture. For a new use case in a project that already follows it, use `vertical-slice-feature`. If that skill is not installed, follow the feature folder contract documented in step 4 and copy the reference slice; do not re-run this setup.
